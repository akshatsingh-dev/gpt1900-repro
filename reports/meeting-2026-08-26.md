## Words you will hear, in plain terms

Read this once so nothing in the meeting is a surprise.

**Checkpoint.** A saved copy of the model at a particular point in training.
Like a save file in a game. There are 24 of them.

**Temperature.** A dial for how much the model gambles when picking each word.
At 0 it always picks its top choice, so the same question gives the same answer
every time. Above 0 it rolls a weighted dice, so the same question gives
different answers. GPT-1900 was run at 0.7.

**Seed.** The starting number for that dice. Write it down and anyone can get
the exact same "random" answers again. Lose it and nobody can, including the
people who ran it.

**Deterministic.** Same input, same output, every time. A calculator is
deterministic. A model at temperature 0.7 is not.

**Reproducible.** Someone else runs it and gets your number. This is the bar
science actually cares about.

**The judge.** They did not grade the answers by hand. They sent them to the
Claude API and had it score each one from 0 to 5. So the grader is itself an AI.

## Findings so far

### 0. The headline: zero of 96 paired answers reproduce

**Plain words.** They have two folders holding the same test, run twice, on the
same 12 saved models. I checked that both runs were asked exactly the same
questions. They were, all 96. Then I compared the answers. Not one of the 96
matched.

**Detail.** `results/physics_eval_v8` and `results/physics_eval_v8_det` share an
identical 12-checkpoint set, 8 tasks each. Prompts identical in 96 of 96 pairs.
Generated answers identical in 0 of 96. [E013, E014]

Set beside the other pair in the repository, `v11` against `v11_replication` at
2 identical out of 24, the combined figure is **2 out of 120 paired answers,
1.7 percent**.

**What I am not claiming.** Not that the model is bad at physics. This measures
repeatability, not ability. And not that I know which run used randomness,
because no file records temperature or a seed. I can show the answers do not
repeat. I cannot show why, and the reason I cannot is itself the problem.

**What it rules out.** The 96 of 96 prompt match rules out the two folders
holding different questions. The 0 of 96 answer match rules out one file being
a copy of the other.

**Why it matters.** The published 0.93 out of 5 rests on 192 answers from this
same pipeline. One unrepeatable draw, from a distribution nobody recorded.

One more thing worth flagging. The folder is named `_det`, which usually stands
for deterministic. Whatever it was meant to test, it does not match `v8` on a
single one of 96 answers. I would like to ask Michael Hla what it was for
before I assume anything.

### 0b. The way the answers differ suggests the fix is small

**Plain words.** I looked at *how* the 96 pairs differ, not just that they do.
The two runs agree for about three words on average, then split. Sometimes they
agree for one character, sometimes for 86.

**Detail.** Shared opening characters across the 96 pairs: shortest 1, longest
86, mean 16. Example, checkpoint `s070` on `sr_train_lightning`, both wrote
"Is it not clear that the train observer sees the two flashes arrive at the same
time", then one continued "in the same space?" and the other "because he sees
them arrive at the same speed in the two inertia frames?". [E015]

**Why the varying split point is the informative part.** If the two runs used
different code, a different checkpoint or different precision, they would differ
at the very first character every time. A split point that wanders between 1 and
86 is what word-by-word randomness produces: the model is confident at some
positions and near-tied at others.

**What that means.** It points at randomness being switched on rather than
something structural being broken. That is the better problem to have, because
the fix is recording a seed rather than rebuilding the pipeline.

I want to put this as a lean, not a finding. Neither file records the settings,
so I am reading this off the output rather than off a recorded parameter. Next
step is reading their eval code to confirm it at the source.

## What "reproducible" actually means here

Worth agreeing on early, because the word covers four different claims and they
are not equally hard.

| Level | The claim | Who can check it |
|---|---|---|
| 1. Repeatable | Same machine, same settings, run twice, same text | Them, from files they already have |
| 2. Deterministic | Same machine, randomness switched off, same text | Them, or me once I have a checkpoint |
| 3. Portable | Different machine, same code and model, same text | Only me, on my hardware |
| 4. Replicable | Someone rebuilds it differently, same conclusion | Nobody yet |

**Plain words.** Level 1 is "I can do it again." Level 3 is "you can do it
too." The paper needs level 3. A result that only works on the machine that
made it is not something anyone can build on.

This matters for how we read their files. If one of their runs happens to
contain the same question answered twice, that gives us level 1 or 2 for free.
It is a real head start. It says nothing about level 3, so it does not replace
running it here.

## Things that can make the same question give a different answer

Listing these so the group can tell me which count as normal variation and which
count as a defect. The physicists in the room will have better instincts than I
do about which of these could change a scientific conclusion versus which just
change the wording.

**The dice**
- Temperature above 0 makes word choice a weighted gamble.
- The seed is never recorded, so nobody can replay the gamble.
- `top_k` and `top_p`, two more settings that narrow the model's choices, are
  typed on the command line and never saved with the results.

**The hardware**
- A graphics card, a normal processor and an Apple chip round numbers
  differently.
- Precision settings, fp32 against bf16, change results with identical code.
- Adding decimals in a different order gives a different final digit. That is
  enough to flip a word choice.
- Running one question alone versus eight at once changes that order.

**The software**
- Different versions of PyTorch or the tokenizer.
- The tokenizer is the part that chops text into pieces before the model sees
  it. A different version chops differently and everything after that changes.

**Which model, exactly**
- Hugging Face model names can be overwritten. The owner can upload new weights
  under the same name. The fix is recording the version id, not just the name.
- The collection mixes plain and RL-tuned checkpoints, and which one made the
  published number is not written down.

**The grader, which I think nobody has raised**
- The scores come from the Claude API, which is a hosted model that gets
  updated over time.
- You could freeze the answers perfectly and the scores would still move,
  because the grader changed underneath you.
- No grader version is recorded anywhere in the results.
- There is one grader and no human check, so there is no way to tell a real
  score change from the grader drifting.

My instinct is that the grader should be pinned like any other instrument, but
I would rather hear the group's view than assume I am right.
